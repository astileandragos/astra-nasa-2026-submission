# ASTRA data contract (v1 proposal)

**Status: v1, implemented by the backend, the dashboard and the firmware (14-15 Nov 2026).** Field names, units, paths and labels are the ones used in the code and the tests.

Owner: Aștilean Dragoș. This replaces the older team proposal where they differ (`spo2_percent`, not `spo2_pct`).

## 1. How the data flows
```
MAX30102 + ICM-20948 -> ESP32 --(HTTP POST JSON, local Wi-Fi 2.4 GHz)--> Flask on laptop -> SQLite -> dashboard (GET)
```

## 2. Network (placeholders, fill in on site)
| Item | Value |
|---|---|
| Base URL | `http://<LAPTOP_IP>:5000` |
| Laptop IP | `<LAPTOP_IP>` (find it with `ipconfig`, the IPv4 address of the Wi-Fi adapter) |
| Port | `5000` |
| Wi-Fi | one 2.4 GHz network that the laptop and the ESP32 share (hotspot as backup) |

- The server must listen on all interfaces (`host="0.0.0.0"`), otherwise the ESP32 cannot reach it. Windows Firewall may ask to allow Python on private networks: allow it.
- Râpan Andrei keeps the URL and the Wi-Fi password in `secrets.h` (git-ignored), never in the repo.

## 3. Rules that apply to everything
1. **Missing data is `null`. Never `0`.** If a sensor value is missing, invalid or not measured (no finger on the MAX30102, sensor not detected, reading failed), send that field as `null`. `0` is a real value and must never mean "missing". This applies to every field in every endpoint.
2. **The server decides the time.** The ESP32 has no reliable clock, so it sends no timestamp. The backend stores the **server time of receipt** (`received_at`, ISO 8601 with time zone, for example `2026-11-14T12:30:00+02:00`) for every measurement and returns it in the responses.
3. **Source label on every record**, always one of the values in section 4. Different sources are never mixed in one record or one chart series without a visible label.
4. **No medical claims.** Heart rate and SpO2 from the MAX30102 are experimental estimates. This contract defines no medical thresholds. The only "ranges" in it are technical checks that reject impossible values (section 5).
5. Same field names and units in firmware, backend and frontend. JSON keys are `snake_case`. Requests and responses use `Content-Type: application/json`.

## 4. Source labels (final spelling)
| Value in JSON | Meaning | Dashboard shows |
|---|---|---|
| `live_hardware` | Measured now by the ESP32 sensors | LIVE – HARDWARE |
| `self_reported` | Typed in by the person (journal) | SELF-REPORTED |
| `simulated` | Generated by the simulator or test data | SIMULATED |
| `external` | Imported from an outside dataset (for example NASA) | EXTERNAL DATA |

- **`self_reported` is the final label** (the brief's `user_reported` is dropped, one spelling everywhere).
- `external` is proposed here because Ciolea Daniel's task sheet mentions external data and the brief's list has no label for it. Ciolea Daniel confirms or removes it.
- Demo or simulated values must never carry `live_hardware`.

## 5. Sensor measurement (ESP32 -> backend)

### Fields the ESP32 sends
| Field | Type | Unit | Notes |
|---|---|---|---|
| `device_id` | string | – | for example `"ASTRA-01"` |
| `heart_rate_bpm` | number or `null` | beats per minute | estimate from the MAX30102 |
| `spo2_percent` | number or `null` | percent (%) | **estimate** from the MAX30102 |
| `accel_x_g`, `accel_y_g`, `accel_z_g` | number or `null` | g (1 g = 9.81 m/s²) | ICM-20948 accelerometer |
| `gyro_x_dps`, `gyro_y_dps`, `gyro_z_dps` | number or `null` | degrees per second | ICM-20948 gyroscope |
| `signal_quality` | string | – | `"good"`, `"poor"`, `"no_finger"`, `"unknown"`. Report only what the firmware really computes, otherwise `"unknown"` |
| `source` | string | – | `"live_hardware"` from the ESP32 (section 4) |
| `uptime_ms` | integer, optional | milliseconds | time since the ESP32 booted (`millis()`). Optional, useful to see gaps. It is **not** a wall-clock time |

The ESP32 does **not** send a timestamp (section 3, rule 2).

```json
{

  "heart_rate_bpm": 72,
  "spo2_percent": 98,
  "accel_x_g": 0.01,
  "accel_y_g": 0.02,
  "accel_z_g": 0.99,
  "gyro_x_dps": 0.2,
  "gyro_y_dps": 0.1,
  "gyro_z_dps": 0.3,
  "signal_quality": "good",
  "source": "live_hardware",
  "uptime_ms": 123456
}
```
(Fictional values.)

```json
{

  "heart_rate_bpm": null,
  "spo2_percent": null,
  "accel_x_g": 0.01,
  "accel_y_g": 0.02,
  "accel_z_g": 0.99,
  "gyro_x_dps": 0.2,
  "gyro_y_dps": 0.1,
  "gyro_z_dps": 0.3,
  "signal_quality": "no_finger",
  "source": "live_hardware",

}
```

### Technical validation on the server (not medical thresholds)
The backend rejects only values that are physically or technically impossible, to protect the database from garbage. These are sanity limits, not health ranges, and they are not shown to the user as health advice.
- `heart_rate_bpm`: number greater than 0 and at most 300, or `null`.
- `spo2_percent`: number greater than 0 and at most 100, or `null`.
- `accel_*_g`: number between -16 and 16, or `null`. `gyro_*_dps`: number between -2000 and 2000, or `null`. (Typical full-scale ranges of the sensor; Râpan Andrei confirms the configured range.)
- A value of `0` for `heart_rate_bpm` or `spo2_percent` is rejected with a message telling the sender to use `null`.
- `source` must be one of the labels in section 4. `signal_quality` one of the four values above.

## 6. Endpoints

All paths start with the base URL. Times in responses are ISO 8601 with time zone.

### 6.1 `GET /api/health`
Check that the server runs (use it from a browser or from the ESP32 before posting).
Response `200`:
```json
{ "status": "ok" }
```

### 6.2 `POST /api/measurements`  (ESP32 or simulator -> backend)
Body: the payload in section 5. Required: `device_id`, `source`. Every sensor field may be `null`, but a field that is absent is treated as `null`.

Success `201`:
```json
{ "status": "ok", "id": 42, "received_at": "2026-11-14T12:30:00+02:00" }
```
Error `400` (same shape for every error in this API):
```json
{ "status": "error", "message": "heart_rate_bpm must be a number between 1 and 300 or null (use null, not 0, for missing data)", "field": "heart_rate_bpm" }
```
An invalid post never stops the server. Firmware: on `201` carry on, on any other status or a network error print a line to Serial and retry on the next cycle.

### 6.3 `GET /api/measurements/latest`  (dashboard)
Optional query `source=live_hardware|simulated|external|self_reported`: return the latest record of that source (`404` if there is none). Without it, the latest record of any source, so the dashboard should always pass `source` and never mix sources on one card.
Response `200`: the record, including the fields the server adds (`id`, `received_at`):
```json
{
  "id": 42,
  "received_at": "2026-11-14T12:30:00+02:00",
  "device_id": "ASTRA-01",
  "heart_rate_bpm": 72,
  "spo2_percent": 98,
  "accel_x_g": 0.01,
  "accel_y_g": 0.02,
  "accel_z_g": 0.99,
  "gyro_x_dps": 0.2,
  "gyro_y_dps": 0.1,
  "gyro_z_dps": 0.3,
  "signal_quality": "good",
  "source": "live_hardware",
  "uptime_ms": 123456
}
```
If there is no data yet: `404` with `{ "status": "error", "message": "no measurements yet" }`. The dashboard shows "waiting for data".

### 6.4 `GET /api/measurements`  (recent history, for charts)
Query parameters (all optional):
| Parameter | Meaning | Default |
|---|---|---|
| `limit` | maximum number of records. Above 100 is capped at 100. Below 1 or not a number gives `400` | `50` |
| `source` | filter by source label (must be one from section 4, otherwise `400`) | all |
| `since` | only records received after this ISO 8601 time, for example `2026-11-14T12:30:00+02:00`. In a URL write the `+` as `%2B` (or use `Z` for UTC). A time without a zone is read as the laptop's time zone. Invalid gives `400` | none |

Response `200`: a **JSON array**, **newest first** (the frontend reverses it to plot oldest to newest). An empty database gives `[]`.
```json
[ { "...": "same record shape as 6.3" }, { "...": "..." } ]
```
`null` values stay `null` in the history. The chart shows a gap, not a zero.

### 6.5 `POST /api/journal`  (frontend -> backend, daily self-reported entry)
Stored separately from sensor measurements. The backend sets `source` to `self_reported` and `received_at` itself; the frontend does not send them.

Body:
```json
{
  "date": "2026-11-14",
  "sleep_hours": 6.5,
  "mood": 3,
  "energy": 4,
  "stress": 2,
  "fatigue": 3,
  "note": "optional free text"
}
```
| Field | Type | Unit / scale | Notes |
|---|---|---|---|
| `date` | string `YYYY-MM-DD` | – | the day the entry is about. One entry per day: posting the same date again replaces it |
| `sleep_hours` | number or `null` | hours | technical check: 0 to 24 |
| `mood` | integer or `null` | 1 to 5 | proposed scale: 1 = lowest, 5 = highest. Ioja Dănuț shows the same labels in the form |
| `energy` | integer or `null` | 1 to 5 | same scale |
| `stress` | integer or `null` | 1 to 5 | same scale (1 = lowest stress, 5 = highest) |
| `fatigue` | integer or `null` | 1 to 5 | same scale (1 = lowest fatigue, 5 = highest). Added 14 Nov from the ASTRA features document (daily check-in F14) |
| `note` | string or `null` | – | optional, at most 500 characters |

Skipped questions are `null`, never `0`. At least one of `sleep_hours`, `mood`, `energy`, `stress`, `fatigue` must be answered. Unknown fields are ignored. Success `201`: `{ "status": "ok", "date": "2026-11-14", "received_at": "..." }`. Errors use the shape in 6.2. Entries typed by a person are always stored as `self_reported`; only the demo seed script writes `simulated` entries.

### 6.6 `GET /api/journal`
Query: `date=YYYY-MM-DD` returns that day's entry; without it, the last entries.
- With `date`, response `200`: the entry plus `source` (`self_reported`, or `simulated` for seeded demo entries) and `received_at`. `404` if none for that day.
- Without `date`, optional `limit` (default `30`), response `200`: `{ "count": N, "items": [ ... ] }`, newest first.
```json
{
  "date": "2026-11-14",
  "sleep_hours": 6.5,
  "mood": 3,
  "energy": 4,
  "stress": 2,
  "fatigue": 3,
  "note": "optional free text",
  "source": "self_reported",
  "received_at": "2026-11-14T21:10:00+02:00"
}
```

### 6.7 Analysis endpoints (read only, simulated data first)
All of them take `source` (default `live_hardware`; `simulated` for simulated data only; `dashboard` for the demo view, which combines a labelled simulated baseline of the earlier days with today's live data, or with today's simulated data when no live reading arrived today). With `live_hardware` or `simulated` an answer uses one source only. The stored records always keep their own label, and the answer repeats `source`. `date` (default today, `YYYY-MM-DD`) is the day being looked at. Errors use the shape in 6.2. Every statistic uses only readings with `signal_quality: "good"` and a non-null value; `null` is never counted as `0`. These are descriptive statistics of the person's own data, not medical thresholds.

#### `GET /api/quality?source=&days=7&date=`  (data quality, F13)
`days` 1 to 30, default 7. Response `200`:
```json
{
  "source": "simulated", "date": "2026-11-14", "days": 7,
  "total": 672,
  "signal_quality": { "good": 600, "poor": 40, "no_finger": 25, "unknown": 7 },
  "missing": { "heart_rate_bpm": 32, "spo2_percent": 32, "motion": 0 },
  "good_share": 0.893,
  "last_received_at": "2026-11-14T13:00:00+02:00",
  "per_day": [ { "date": "2026-11-08", "total": 96, "good": 85, "missing_heart_rate": 4 } ]
}
```
`good_share` is `null` when there are no readings. `per_day` has one entry per day, oldest first, with zeros for days without data.

#### `GET /api/stats/daily?source=&days=7&date=`  (daily statistics, F01, F03)
Response `200`, oldest day first, a day without good readings has `null` values and `n: 0`:
```json
{
  "source": "simulated", "date": "2026-11-14", "days": 7,
  "per_day": [
    { "date": "2026-11-14",
      "heart_rate_bpm": { "min": 55, "max": 96, "avg": 68.4, "median": 67, "n": 90 },
      "spo2_percent":   { "min": 95, "max": 99, "avg": 97.1, "median": 97, "n": 90 } }
  ]
}
```

#### `GET /api/baseline?source=&days=7&date=`  (personal baseline, F02, F11)
Method: the median of all good-quality heart rate readings on the `days` days **before** `date` (the day itself is excluded). A day counts only with at least 20 good readings, and the baseline needs at least 3 such days. Response `200`:
```json
{
  "source": "simulated", "date": "2026-11-14",
  "method": "median of good-quality heart_rate_bpm readings on the previous days; a day needs 20+ good readings, 3+ days required",
  "ready": true, "days_used": 6, "readings_used": 520,
  "heart_rate_bpm": { "median": 66, "q1": 61, "q3": 72, "daily_medians": [65, 66, 67, 66, 65, 67] },
  "spo2_percent": { "median": 97 },
  "sleep_hours": { "mean": 7.1, "n": 5 }
}
```
When there is not enough data: `"ready": false`, `heart_rate_bpm` and `spo2_percent` are `null`, and `"reason"` says what is missing. `sleep_hours` comes from the daily check-in of the same data family (`self_reported` entries for real sources, `simulated` entries for `source=simulated`) and is `null` with fewer than 3 earlier entries.

#### `GET /api/observation?source=&date=`  (rule-based observations)
Two documented rules, no model, no diagnosis, no medical thresholds. The limit is the person's own variation: **2 x the standard deviation of their own daily medians** (heart rate, never below 1 bpm) or of their own earlier sleep entries (never below 0.5 h). A day needs at least 10 good readings.
- `hr_vs_baseline`: today's median heart rate against the baseline median.
- `sleep_vs_average`: the day's reported sleep against the average of earlier entries.
```json
{
  "source": "simulated", "date": "2026-11-14", "status": "ok",
  "generated_at": "2026-11-14T13:00:00+02:00",
  "observations": [
    { "id": "hr_vs_baseline", "level": "notable",
      "message": "Today's median heart rate (74 bpm) is higher than your baseline (66 bpm).",
      "based_on": { "metric": "heart_rate_bpm", "today_median": 74, "baseline_median": 66,
                    "difference": 8, "limit": 3.2, "readings_today": 42, "baseline_days": 6,
                    "period": { "from": "2026-11-08", "to": "2026-11-13" } },
      "rule": "notable when |today median - baseline median| is more than 2 x the standard deviation of your own daily medians",
      "suggested_step": "Add a note about sleep, activity or stress to the daily check-in for context." }
  ],
  "disclaimer": "Educational prototype. This is not a diagnosis or medical advice."
}
```
`level` is `info` (within the person's usual variation) or `notable`. `status` is `insufficient_data` (with `observations: []` and a `reason`) when the baseline is not ready or the day has fewer than 10 good readings.

#### `GET /api/activity?source=&date=&window_min=30`  (activity, F05, experimental)
`window_min` 5 to 120, default 30. For each window of the day: `movement_index`, the mean of `|acceleration magnitude - 1 g|` over readings with all three axes present, in g (an **experimental** indicator of movement, not a clinical measure), and `n` readings. Windows without readings have `null`.
```json
{
  "source": "simulated", "date": "2026-11-14", "window_min": 30,
  "windows": [ { "start": "00:00", "movement_index": 0.012, "n": 12 }, { "start": "00:30", "movement_index": null, "n": 0 } ]
}
```

### 6.8 `GET /api/status?source=&stale_after=10`  (freshness, for an offline or stale warning)
`source` default `live_hardware`. `stale_after` in seconds, 1 to 3600, default 10 (five readings at the suggested 2 s interval). Response `200`:
```json
{
  "source": "live_hardware", "server_time": "2026-11-14T13:00:05+02:00", "total": 1280,
  "last_received_at": "2026-11-14T13:00:03+02:00", "seconds_since_last": 2.0,
  "latest_signal_quality": "good", "median_interval_seconds": 2.0,
  "stale_after_seconds": 10, "stale": false
}
```
`stale` is `true` when the last reading is older than `stale_after` seconds or there is none. `median_interval_seconds` is the median gap between the last 50 readings (it answers the open "sampling interval" question with real data). The dashboard shows a warning when `stale` is `true`, or when this request itself fails (server down). It never presents an old value as live.

### 6.9 `GET /api/export.csv?kind=&source=&days=7&date=`  (CSV for a spreadsheet)
`kind` is `measurements` (default) or `journal`. `source` default `simulated` (as everywhere, one source per file). `days` 1 to 365. The answer is a file download (`text/csv`, `Content-Disposition: attachment`). Columns are the record fields of 6.3 (measurements) or 6.5 and 6.6 (journal). **A missing value is an empty cell, never `0`.** Text that starts with `=`, `+`, `-` or `@` gets a leading `'` so a spreadsheet does not run it as a formula. At most 50000 rows.

### 6.10 `GET /api/reference?topic=`  (external references, never measurements)
Curated references from `data/reference.json`: published papers and public datasets with what was read from them and what they cannot be compared with. Not stored in the measurements table, so it can never mix with `live_hardware`, `simulated` or `self_reported` rows. Response `200`:
```json
{
  "count": 3, "source": "external",
  "items": [
    { "id": "i4-cardiovascular-paper", "title": "...", "kind": "literature", "mission": "...",
      "source_url": "https://...", "access": "...", "retrieved": "2026-11-14", "status": "needs_review",
      "statements": ["..."], "cannot_be_compared": ["..."],
      "label": "external", "note": "Extracted from the literature or a public dataset page. Not live telemetry and not ASTRA data." }
  ]
}
```
`kind` is `literature` or `dataset`. `status` is `needs_review` until a teammate has checked the entry against the source (`reviewed`). The panel must show `source_url`, the `cannot_be_compared` points and the `note`, and must label everything EXTERNAL DATA. Only facts that were read from the source are in the file: no per-phase heart rate numbers have been extracted yet, so none are shown. Ciolea Daniel extends the file after reading the sources (same structure, `id` unique, `https` link, at least one statement and one limitation).

### 6.11 `GET /api/timeline?source=&days=7&date=`  (unified timeline, read only)
One row per day, oldest first, combining the three kinds of information in one answer: the daily median heart rate (good-quality readings only), the mean movement index (experimental, see 6.7 activity), and the self-reported check-in of that day. Measurements come from `source` and the check-in from the matching family (`self_reported` entries for real sources, `simulated` entries for `source=simulated`), so nothing is mixed. `days` 1 to 30, default 7.
```json
{
  "source": "simulated", "date": "2026-11-14", "days": 7,
  "baseline": { "median": 70, "q1": 63, "q3": 74, "days_used": 6 },
  "per_day": [
    { "date": "2026-11-14", "readings": 380,
      "heart_rate_bpm": { "median": 75, "n": 340 },
      "movement_index": 0.021,
      "checkin": { "date": "2026-11-14", "sleep_hours": 7, "mood": 4, "energy": 3, "stress": 2, "fatigue": 4, "source": "self_reported" } }
  ]
}
```
`baseline` is `null` until the baseline is ready. A day without data has `readings: 0`, `median: null`, `movement_index: null`; a day without a check-in has `checkin: null`. Never `0` for missing.

### 6.12 `GET /api/rest?source=&nights=7&date=`  (rest from movement, experimental, read only)
Finds the rest period of each night from the ICM-20948 movement only. It is **not** sleep staging and **not** a diagnosis. The night "ending on" a date runs from 18:00 the day before to 12:00. It is cut into 30 minute windows; a window is "still" when at least 80% of its motion readings are within 0.05 g of 1 g (windows with fewer than 2 motion readings are `no data`). The rest period is the longest still stretch of at least 2 hours; one moving window inside it counts as one wake-up. A night needs motion readings in at least 75% of its windows, otherwise it is `insufficient_data`. `nights` 1 to 14, default 7, oldest first, `source` default `live_hardware`.
```json
{
  "source": "simulated", "date": "2026-11-14", "nights": 7,
  "method": "...", "limits": "...", "disclaimer": "...",
  "per_night": [
    { "date": "2026-11-14", "status": "ok", "coverage": 1.0, "rest_start": "23:30", "rest_end": "06:30",
      "start_minutes": 330, "duration_h": 7, "wake_ups": 1,
      "resting_heart_rate": { "median": 60, "n": 25 } },
    { "date": "2026-11-08", "status": "insufficient_data", "coverage": 0.67, "rest_start": null, "rest_end": null,
      "start_minutes": null, "duration_h": null, "wake_ups": null, "resting_heart_rate": null,
      "reason": "only 67% of the night has motion readings, 75% needed" }
  ],
  "usual": { "nights_used": 5, "start_median": "23:00", "start_spread_min": 39.9, "start_range_min": 120,
             "end_median": "06:15", "end_spread_min": 36.3 }
}
```
`start_minutes` counts minutes after 18:00 on the day before (so a start after midnight is above 360). `resting_heart_rate` is the median of good-quality heart rate readings inside the still windows. `usual` is the median and the spread (standard deviation, minutes) of the earlier nights and is `null` until 3 earlier nights are usable. Nothing is filled with `0`: a night without enough data has `null` values and a `reason`.

**Observation:** `GET /api/observation` adds a third rule, `rest_start_vs_usual` (metric `rest_start`), when last night and at least 3 earlier nights are usable: notable when |last rest start - median of earlier rest starts| is more than 2 x the standard deviation of the earlier starts (at least 30 minutes). It has the same fields as the other observations (`message`, `based_on`, `rule`, `level`, optional `suggested_step`).

### 6.13 `GET /api/wear?source=&days=7&date=`  (wear time, read only)
How complete each day is. A 30 minute window counts when it has at least one reading from this device; `coverage` is counted windows divided by the windows of the day (for today: until now). `enough` is true when coverage is at least 80%. `days` 1 to 30, default 7, oldest first.
```json
{
  "source": "simulated", "date": "2026-11-14", "days": 7, "days_enough": 7, "method": "...", "why": "...",
  "per_day": [
    { "date": "2026-11-14", "readings": 196, "data_hours": 16.5, "heart_rate_hours": 16.5,
      "coverage": 1.0, "longest_gap_h": 0.1, "enough": true }
  ]
}
```
`heart_rate_hours` counts windows with a good-quality heart rate. `longest_gap_h` is the longest time without any reading during the day (`null` when the day has no readings). A day with no readings has `coverage: 0` and `enough: false`.

### 6.14 `GET /api/notifications?source=&date=`  (traffic-light notifications and daily suggestions, read only)
One answer for the Overview page: a list of `notifications` (sorted red, orange, green) and a list of `suggestions`. Both come from documented rules on the data of ONE `source` (default `live_hardware`), never from a prediction model. Every item names the page to open and carries the advice shown there, so the Overview can link to it and the target page can explain what to do.
```json
{
  "source": "simulated", "date": "2026-11-14", "generated_at": "2026-11-14T16:36:08+02:00",
  "summary": { "danger": 1, "warning": 1, "ok": 3 },
  "notifications": [
    { "id": "hr_vs_baseline", "level": "danger", "title": "Heart rate higher than your baseline",
      "message": "Today's median 75 bpm, baseline 71 bpm (+4 bpm, limit ±1.8).",
      "page": "timeline.html", "target": "hr-h",
      "advice": { "meaning": "...", "steps": ["Sit down for 5 minutes, ...", "..."] } }
  ],
  "suggestions": [
    { "id": "s_checkin", "title": "Fill in today's check-in", "text": "Two minutes: ...",
      "page": "journal.html", "target": "form-h", "advice": { "meaning": "...", "steps": ["..."] } }
  ],
  "disclaimer": "Educational prototype. This is not a diagnosis or medical advice."
}
```
**Levels** (they say what to do, not a medical judgement): `ok` nothing to do (`steps` is an empty list), `warning` look at it when you can, `danger` needs action now.

| id | rule | levels |
|---|---|---|
| `connection` (only when `date` is today) | time since the last reading of this source | ok up to 10 s, warning up to 5 min or when nothing has arrived yet, danger after 5 min |
| `hr_vs_baseline` | the heart rate observation of 6.7 | ok within the usual variation, warning when notable, danger when the difference is more than 2 x the observation limit |
| `rest_start_vs_usual` | rest observation of 6.12 | ok or warning |
| `sleep_vs_average` | sleep observation of 6.7 | ok or warning |
| `signal_quality` | good share of today's readings (needs 10+) | ok at 70% or more, otherwise warning |
| `wear_time` | today's coverage from 6.13 | ok at 80% or more, otherwise warning |
| `baseline` | baseline not ready | ok, with the reason |

**Suggestions** (`s_checkin` when today has no check-in of the matching source, `s_note` when a heart rate, rest or sleep notification is not green, `s_rest` or `s_rest_data`, `s_baseline` until the baseline is ready, and `s_timeline` always) have the same `page`, `target` and `advice` fields. Ids are unique across both lists.

**Routing:** the Overview links every item to `<page>?source=<source>&from=<id>`. **Every measurement page shows the notifications whose `page` is that page at all times** (with or without `from`), refreshed every 5 seconds: status, the meaning, and the numbered `steps`; suggestions for the page are listed too. The panel whose heading has the id `target` is highlighted while its notification is not green. With `from=<id>` for an id that is no longer in the answer, the page says the item is no longer active. The red heart rate advice ends with a step to tell a colleague or medical staff if the person feels unwell; ASTRA never assesses health.

### 6.15 Radiation Risk Monitor `/api/radiation/...`  (docs/RADIATION_MONITOR.md)
Space weather alerts and an illustrative exposure budget. Read `docs/RADIATION_MONITOR.md` for the science. **Proton flux is not dose and the budget is not a medical result.** `source` is `external` (NOAA GOES proton flux, the default) or `simulated` (a team scenario); the two are never mixed (separate samples, separate budgets). Times are UTC. Unrelated to the heart rate, SpO2 and movement data.

| Endpoint | Answer |
|---|---|
| `GET /api/radiation/status?source=` | current state, see below |
| `GET /api/radiation/flux?source=&hours=24` | `hours` 1 to 168; `samples: [{time, flux_pfu, s_class}]`, `thresholds` (S1 10, S2 100, S3 1000, S4 10000, S5 100000 pfu), `channel: ">=10 MeV"` |
| `GET /api/radiation/events?source=&days=7` | `events` and `alerts`, newest first |
| `GET /api/radiation/alert?source=` | compact answer for the ESP32 OLED (below) |
| `POST /api/radiation/ack` | body `{"alert_id": "..."}`; `404` for an unknown id. Does not change the level |
| `POST /api/radiation/refresh` | fetch NOAA now: `{inserted, skipped, error, file}`; `502` if NOAA could not be reached (old data stays) |
| `POST /api/radiation/simulate` | body `{"scenario": "quiet|s1|s2|s3|s4|history"}` (replaces the simulated flux with a storm at its peak now) or `{"flux_pfu": number}` (adds one sample). Simulated data only |
| `GET /api/radiation/budget?source=` | the exposure estimate against NASA's career limit (below) |
| `POST /api/radiation/budget?source=` | body with any of `budget_msv`, `initial_msv`, `baseline_rate_msv_day` |
| `POST /api/radiation/dose?source=` | body `{"msv": number > 0, "note": "text"}`: an operator-entered dose (label `self_reported`) |

**Status**
```json
{ "source": "simulated", "data_status": "ok", "data_age_min": 2.1, "last_fetch_at": null, "fetch_error": null,
  "state": { "level": 3, "level_name": "SEVERE", "s_class_now": 4, "flux_pfu": 38759.158, "last_sample_at": "2026-11-14T16:11:00+00:00",
             "event_id": "simulated:20261114T125600Z", "event_started_at": "...", "s_class_peak": 4 },
  "alert": { "level": 3, "name": "SEVERE", "summary": "...", "actions": ["Go to the designated radiation shelter immediately.", "..."] },
  "ack_pending": { "alert_id": "simulated:20261114T125600Z:3", "title": "..." },
  "oled": { "lines": ["RAD 3 SEVERE", "S4 38759 pfu >=10MeV", "SHELTER NOW", "Await mission ctrl"], "footer": "BTN = ACKNOWLEDGE",
            "beep": "continuous", "repeat_until_ack": true },
  "thresholds": [ ... ], "what_it_is": "...", "disclaimer": "..." }
```
`data_status`: `ok` (newest sample at most 15 min old), `delayed` (up to 2 h), `stale`, `no_data`. With no data `flux_pfu` and `s_class_now` are `null`, never 0. The level is **held** when data is late; missing data never clears an alert.

**Levels** (ASTRA demonstration states, not NASA flight rules): 0 NORMAL (below S1), 1 ELEVATED (S1), 2 HIGH (S2, S3), 3 SEVERE (S4, S5). Rules: onset after 3 consecutive 5-minute samples at or above S1; escalation after 2 consecutive samples above the current level; easing or recovery after 6 consecutive samples lower than the level judged with thresholds x 0.5; a gap over 30 minutes restarts the counters.

**Alert object** (`events` and `alerts` lists): `{id, source, event_id, at, kind: onset|escalation|easing|recovery, level, s_class, flux_pfu, title, message, actions[], requires_ack, acknowledged_at}`. The id is `source:event-start-compact:sequence`, derived from the samples, so an alert exists only once. Onset and escalation require an acknowledgement; easing and recovery are information only.

**ESP32 alert** (`GET /api/radiation/alert`): `{source, level, s_class, data_status, alert_id, ack_pending, lines[4] (each at most 21 characters), footer, beep: none|short|double|continuous, repeat_until_ack, updated_at}`. The firmware draws `lines` and `footer`, sounds `beep` only while `ack_pending`, and posts the `alert_id` to `/api/radiation/ack` when the button is pressed.

**Budget** (`kind: "illustrative_model"`): `D_remaining = D_budget - D_accumulated`, `T = D_remaining / R_projected`. Fields: `budget_msv`, `initial_msv`, `baseline_rate_msv_day`, `baseline_accrued_msv`, `event_dose_msv`, `accumulated_msv`, `remaining_msv`, `used_share`, `exceeded`, `estimated_days_remaining` (`null` when the background rate is 0), `why_it_changed` (one sentence), `entries[]` (`at`, `msv`, `origin: simulated_event|operator_entered`, `label: simulated|self_reported`, `remaining_before_msv`, `remaining_after_msv`, `days_before`, `days_after`, `note`), `assumptions[]`, `dose_status`. Dose is **never computed from flux**: a simulated event adds the illustrative demonstration dose of its S class (0.1, 1, 5, 20, 60 mSv for S1 to S5, a team choice); a real NOAA event adds nothing by itself.

**Exposure estimate** (`GET /api/radiation/budget`): `budget_msv` is NASA's career effective dose limit, 600 mSv by default (NASA-STD-3001 Vol 1 [V1 4030]); `initial_msv` is the dose already received (0 until the user enters it); `baseline_rate_msv_day` is an assumed background rate (default 0.5). New fields: `daily_background_msv`, `daily_event_msv_24h` (event doses of the last 24 hours), `daily_exposure_msv` (their sum) and `daily` (the last 7 UTC days, each `{date, background_msv, event_msv, total_msv}`). `kind` is `estimate`. `daily_background_msv` and each day's `background_msv` vary by up to 35% around `baseline_rate_msv_day` (a deterministic simulated variation per day; the total uses the average rate). New settings `mission_days` (default 180) and `mission_day` (default 73, the demo mission) give `mission: {assumed, days_total, day_now, days_left, projected_total_msv, limit_msv, within_limit, note}`; `initial_msv` defaults to 36.5 (73 days x 0.5). Event doses are simulated (demo) or typed in (`POST /api/radiation/dose`); dose is never computed from NOAA flux. The scenario `history` fills the simulated source with a quiet week and three past events (S1, S2, S1).

**Overview notification:** `GET /api/notifications` (6.14) includes an item `radiation` (page `radiation.html`, target `rad-status-h`) when an event is active in either source (level 1 orange, level 2 and 3 red, with advice steps) or when fresh NOAA data is quiet (green). Two more ids exist: `radiation_data` (warning, "Radiation data unavailable", for stale or missing data; it never says normal) and `radiation_recovery` (ok, for 6 hours after the event ended). The signal-quality and connection items use page `sensors.html`, target `alert-h`.

Reference items have an optional `topics` list (any of `radiation`, `cardiovascular`, `sleep_activity`, `isolation_behavior`, `human_spaceflight`, `countermeasures`; `[]` when none) and `?topic=` keeps only the items with that topic (`400` for an unknown topic).

### 6.16 `GET /api/osdr/search?q=&type=all&size=10`  (NASA OSDR study search, external, read only)
Searches the study metadata of NASA's Open Science Data Repository through its public search API (`https://osdr.nasa.gov/osdr/data/search`). Needs internet. Everything returned has `label: "external"` and is **never mixed with measurements**. See `docs/OSDR_RESOURCES.md`.
- `q`: 2 to 100 characters (letters, digits, spaces and `. , - _ + '`), otherwise `400`.
- `type`: `cgene` (NASA GeneLab), `alsda` (NASA Ames Life Sciences Data Archive) or `all` (default; results alternate between the two). `esa` is not supported by the API.
- `size`: 1 to 20 results, default 10.
```json
{ "query": "radiation heart", "type": "all", "total": 17, "shown": 10, "cached": false, "source": "external",
  "source_name": "NASA Open Science Data Repository (OSDR)", "note": "...",
  "results": [ { "accession": "OSD-435", "title": "...", "organism": "Mus musculus", "material": "Heart and Abdominal Aorta",
                 "factors": "Ionizing Radiation", "released": "2023-05-24", "summary": "(up to 320 characters)",
                 "data_type": "alsda", "data_type_name": "NASA Ames Life Sciences Data Archive",
                 "url": "https://osdr.nasa.gov/bio/repo/data/studies/OSD-435", "label": "external" } ] }
```
A missing or placeholder release date is `null`. Results are cached for 10 minutes. If NASA cannot be reached the answer is `502` with `{ "status": "error", "message": "NASA OSDR could not be reached. Try again later." }`. The study text is returned unchanged and must be shown as plain text.

**Dashboard view (16 Nov 2026).** `source=dashboard` is accepted by the measurement, analysis, notification, status and export endpoints. It reads the earlier days from `simulated` and today from `live_hardware` if any live reading arrived today, otherwise from `simulated`. `GET /api/demo/status` returns `{date, baseline_source, baseline_days, today_source, today_readings}`. `POST /api/demo/reset-today` deletes today's `live_hardware` and `simulated` readings and today's check-in (earlier days are never touched) and returns `{removed_readings, removed_checkins}`.

**Radiation outlook (16 Nov 2026).** `GET /api/radiation/outlook?source=external|simulated` returns `{stage: {key (clear|watch|prepare|build|shelter|unknown), index, title, headline, steps: [{text, tag nasa|astra}]}, stages, signals: [{key, active, text}], early_signs_available, limits, sources}`. The scenarios `watch` and `prepare` were added to `POST /api/radiation/simulate`. A notification `radiation_outlook` (warning) appears for the watch and prepare stages.

#### Other behaviour (all endpoints)
- Requests bigger than 64 KB get `413`. An unexpected server error gives `500` with `{ "status": "error", "message": "internal server error" }` as JSON (never an HTML page), and the server keeps running.
- Rejected requests and errors are logged to `backend/astra.log` (field and reason, never the request body).

#### Simulated demo data
`backend/seed_demo.py` fills the database with several days of data labelled `simulated` (device `SEED-SIM`) and `simulated` check-ins, so these endpoints can be demonstrated without hardware. It never writes `live_hardware` rows.

## 8. Status
This contract is implemented by the backend (`backend/`), the dashboard (`frontend/`) and the firmware (`firmware/esp32/`). Decisions: the self-reported label is `self_reported`; the server records the time of receipt and the ESP32 sends no timestamp; NOAA and NASA OSDR data use the `external` label; one reading is sent about every 2 seconds. No formal sign-off by individual reviewers is recorded in this repository.
